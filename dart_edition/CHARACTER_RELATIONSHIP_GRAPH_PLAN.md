# 人物關係圖頁面功能分析與實作規劃

## 1. 文件目的

本文件依照現有 `CharacterView` 的人物資料與關係編輯流程，整理人物關係圖 `RelationshipView` 頁面所需的功能、資料來源、互動方式與實作範圍。

目標是讓使用者能以圖形方式快速理解角色之間的關係，同時保留 `CharacterView` 作為人物資料的主要編輯入口，避免產生兩套互相不一致的角色資料。

相關程式：

- `lib/modules/characterview.dart`
- `lib/modules/relationshipview.dart`
- `lib/models/character_data.dart`
- `lib/models/project_data.dart`
- `lib/models/codecs/character_state_codec.dart`

## 2. 現有 CharacterView 能力

### 2.1 人物資料

目前每個人物使用 `CharacterEntryData` 儲存，具有穩定的 `characterId` 與顯示名稱 `displayName`。若人物名稱重複，`CharacterView` 會在選項中附加 8 碼 `nanoId` 區分人物。

關係圖應以 `characterId` 作為節點識別，不應以顯示名稱作為唯一鍵。

### 2.2 目前關係欄位

每個人物有：

```dart
List<CharacterRelationship> relationships
```

其中每筆資料目前只有：

```dart
CharacterRelationship(
  person: String,
  relationship: String,
)
```

現有 UI 已支援：

- 以表格顯示「人物」與「關係」。
- 新增一筆人物關係。
- 點選既有資料後編輯。
- 直接編輯表格儲存格。
- 刪除選取的關係。
- 同一人物名稱重複輸入時合併描述。
- 載入人物時合併歷史資料中的重複關係。
- 修改後即時寫回目前人物資料。
- 透過 `CharacterView` 的 XML codec 保存與載入。

### 2.3 現有資料限制

目前的關係資料是「由某一人物描述另一人物」的單向文字資料，沒有：

- 目標人物的 `characterId`。
- 強度、信任度或好感度。
- 關係建立時間、結束時間或故事時間點。
- 邊的唯一識別碼。

因此第一版關係圖應採取相容優先的設計，先將可辨識的 `person` 名稱映射到人物節點；無法映射的資料仍需保留並以「未連結人物」呈現。

## 3. 人物關係圖頁面需要的功能

### 3.1 基本視覺化

- 顯示所有人物節點。
- 以單向箭頭連線，表示人物之間的關係。
- 在連線上顯示關係描述。
- 以箭頭或其他視覺提示表示關係方向。
- 節點顯示人物名稱；重複名稱時顯示 `nanoId` 作為區分。
- 沒有任何關係時顯示空狀態，並引導使用者回到 `CharacterView` 新增關係。
- 支援節點過多時的畫布平移與縮放。

### 3.2 節點互動

- 點擊節點後突出顯示該人物。
- 同時突出顯示與該人物相連的節點與連線。
- 顯示人物摘要，例如職業、年齡、性別、人物摘要或關係摘要。
- 提供「開啟人物編輯」入口，跳回 `CharacterView` 並選取該人物。
- 支援從節點開啟關係編輯面板。

### 3.3 連線互動

- 點擊連線後顯示來源人物、目標人物及關係描述。
- 支援編輯關係描述。
- 支援刪除關係，並在刪除前提供確認。
- 當兩個人物之間有多筆不同描述時，應合併顯示或以多條彎曲連線避免完全重疊。
- 對無法對應到現有人物的 `person` 值，提供修正或建立人物的操作。

### 3.4 搜尋與篩選

- 依人物名稱、別名或 `nanoId` 搜尋。
- 依選取人物只顯示一階鄰居。
- 顯示全部關係或只顯示與目前人物相關的關係。
- 關係文字篩選可作為第二階段功能，第一版可先保留 UI 擴充位置。

### 3.5 版面與檢視控制

- 自動排列節點。
- 重新排列後保留目前縮放比例與選取狀態。
- 支援適合畫布、重設縮放、放大、縮小。
- 關係數量較多時避免節點文字及連線完全重疊。
- 於桌面與窄螢幕寬度下維持可操作性。

### 3.6 資料同步與保存

- 關係圖以 `characterDataProvider` 為唯一路徑讀取人物資料。
- 從 `CharacterView` 修改關係後，關係圖應更新。
- 從關係圖修改關係後，應使用既有 `CharacterDataNotifier` 更新人物資料。
- 切換專案時清除舊專案的節點、選取狀態與暫存草稿。
- 匯出與載入時維持現有 XML 格式相容性。
- 任何不能映射的舊資料不可靜默刪除。

## 4. 建議實作範圍

### 4.1 第一階段：可交付的 MVP

第一階段先完成「讀取既有資料並可操作檢視」，不立即改變既有 XML 結構。

### 頁面與狀態

- 新增 `CharacterRelationshipView` 或同等頁面元件。
- 建立關係圖專用的 view model / selector，將 `Map<String, CharacterEntryData>` 轉成 nodes 與 edges。
- 使用 `characterId` 建立節點。
- 使用人物名稱解析 `CharacterRelationship.person` 對應目標節點。
- 對解析不到的名稱建立 dangling / unresolved edge，避免資料遺失。

### 圖形互動

- 在關係圖內新增關係。
- 節點、連線、標籤的基本繪製。
- 畫布平移與縮放。
- 點擊節點顯示人物摘要及相鄰關係。
- 點擊連線顯示關係描述。
- 自動排列與重新排列。
- 搜尋人物與聚焦節點。
- 關係雙向檢視：同一對人物若互相描述，分別顯示兩個方向。
- 在單向連線上顯示關係標籤。
- 從目前選取的人物建立目標人物。
- 連線刪除。
- 納入Undo/Redo列表。

### 與既有頁面整合

- 從節點跳轉至 `CharacterView` 的指定人物。
- 優先重用既有關係編輯邏輯，避免在兩個頁面複製合併、去重與保存規則。
- 若 MVP 需要修改關係，先以既有表格編輯器或共用的關係編輯 panel 實作。

## 5. 關係解析規則

第一版採用以下規則：

1. 節點永遠使用 `characterId`。
2. 先以 `person` 完整比對目前人物顯示名稱。
3. 比對時忽略前後空白與大小寫。
4. 若名稱重複，使用 `nanoId` 輔助選取；不可任意選擇其中一個人物。
5. 若找不到對應人物，建立未連結資料邊並保留原始文字。
6. 不因顯示名稱變更而直接刪除關係；應透過 ID 綁定或提供重新對應流程。
7. 對同一人物的重複關係，沿用 `CharacterView` 現有的合併規則，避免圖上出現不必要的重複邊。

## 6. 元件拆分

將功能拆成以下責任，降低 `characterview.dart` 持續膨脹的風險：

- `character_relationship_graph_view.dart`：頁面與畫布布局。
- `character_relationship_graph_controller.dart`：選取、縮放、篩選及畫布狀態。
- `character_relationship_graph_mapper.dart`：將 `CharacterEntryData` 映射為 graph nodes / edges。
- `character_relationship_editor.dart`：新增、編輯、刪除關係的共用面板。
- `character_relationship_resolver.dart`：名稱、nanoId、未連結人物的解析。
- 共用 `CharacterDataNotifier`：所有資料寫入仍集中在既有 provider。

實際檔名可依專案現有 module 命名規則調整，但應避免把關係圖全部塞入 `CharacterView`。

## 7. 驗收條件

### MVP 驗收

- [ ] 可顯示所有目前人物節點。
- [ ] 可根據 `CharacterView` 已有關係資料繪製連線。
- [ ] 顯示名稱重複時仍能辨識正確人物。
- [ ] 無法解析的關係不會消失，且有明確視覺提示。
- [ ] 可平移、縮放、自動排列與搜尋人物。
- [ ] 點擊節點可查看人物摘要。
- [ ] 可跳轉回指定人物的 `CharacterView` 編輯畫面。
- [ ] 切換人物或專案後不會殘留前一筆選取狀態。
- [ ] 空資料與單一人物資料都有可理解的空狀態。

### 編輯功能驗收

- [ ] 新增、編輯、刪除後 `CharacterView` 與關係圖內容一致。
- [ ] 重複人物關係沿用既有合併規則。
- [ ] XML 匯出再載入後，關係資料仍存在。
- [ ] 刪除人物或改名時，不會靜默刪除無法解析的關係。

## 8. 暫不實作項目

以下功能不列入第一版，除非產品需求明確要求：

- 自動由 AI 推測人物關係。
- 直接修改既有 XML schema 以加入大量關係圖專用欄位。
- 以顯示名稱取代 `characterId` 作為資料關聯鍵。
- 複雜時間軸、關係版本控制與衝突合併。
- 多種圖形布局演算法的完整自訂。
- 圖片匯出、分享與協作編輯。

## 9. 實作結論

人物關係圖第一版應定位為 `CharacterView` 的視覺化延伸：讀取既有 `CharacterData`，將人物轉為節點、將 `relationships` 轉為連線，提供搜尋、聚焦、縮放、摘要查看與跳轉編輯。資料寫入先沿用現有關係結構與 XML codec，並將未能以名稱解析的關係保留下來。

真正需要新增資料模型的部分是「穩定的目標人物 ID、類型與強度」。這些應在 MVP 驗證使用者對關係圖的需求後，再透過版本化 migration 漸進加入，避免第一版破壞現有 `CharacterView` 的資料相容性。
